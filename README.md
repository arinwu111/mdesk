# mdesk

港美股行情数据工作台。一套自己维护的行情与公司行动底稿，附带校验层，保证看到的价格、估值、事件都是可信的。

### ▶ 在线查看：https://arinwu111.github.io/mdesk/

打开即用，无需安装。导航分两组：日常视图 3 个（总览、自选股、事件日历），
运营视图 6 个（异常清单、复权核对、数据覆盖、规则库、处理台账、运营报告）。

想直接看这个项目最核心的产出，去 **[复权核对](https://arinwu111.github.io/mdesk/ops/corpaction.html)**
那一页——它用数据源自己的两个字段，证明了它自己算错了复权价。

---

**它不产生投资观点，只保证观点建立在对的数字上。**

打开一只票发现今天 -48%，第一反应必须是「这是真跌，还是 5 合 1 的合股」。
看到 PE 是 -3，得知道是真亏损还是数据源单位错位。这个工具解决的是这一类问题。

## 首轮跑出来的东西

35 只自选股、两年日线共 19239 行、119 笔公司行动、22 条校验规则。

**数据源的派息金额与它自己的复权价互不自洽。**
阿里巴巴 9988.HK 两次派息全部对不上，汇丰控股 0005.HK 九次中最近一次对不上，
隐含倍数均为 **7.847**，恰好等于港币兑美元的联系汇率。
数据源上报的派息是港币金额（正确），但它算复权价时扣减的是美元金额。

阿里每份 ADS 派息 2.00 美元、对应 8 股港股，每股 0.25 美元。
数据源从 118.80 港币的价格里扣掉了 0.25，而不是应该扣的 1.96 港币。

其余 21 只有派息记录的标的倍数全部为 1.0000，包括腾讯、中国石油这类纯港股，
以及阿里自己的美股 BABA。问题只出在同时有美股 ADR 的港股上。

这个结论只用数据源自己的两个字段就能证明，不需要任何外部资料。
影响是阿里全历史 445 个交易日的复权价偏低最多 2.201%，
任何基于它计算的历史涨跌幅、区间收益、波动率都有系统性偏差。

**港股半日市当天成交量整体缺失。**
平安夜、除夕、农历新年前一日共 6 天，港股标的成交量集体为零。
港交所这几天只有早市。这是市场规则不是数据错误，已归为 P2 并写入 SOP 年度事项。

### 规则是长出来的，不是一次编出来的

每条规则的 `note` 字段都记着它的来历，运营报告第五节自动汇总。三个例子：

**DQ-CA-001** 初版按受影响的每个交易日告警，阿里一个根因刷出 445 条噪声；
改为按除权日定位根因后降到 3 条，另拆出 DQ-CA-004 专门说明影响范围。

**DQ-PRC-003** 初版不区分个股与全市场，港股半日市当天十来只标的一起命中；
加上「同市场同日命中占比」判据后只保留孤立情况，全市场性的交给新增的 DQ-PRC-005。

**DQ-PRC-002** 初版对全部标的统一取 20% 固定阈值，跑出 81 条命中，
其中智谱、OKLO、IONQ 三只高波动标的占了 44%，全是正常波动；
而中国石油这类日波动率仅 1.5% 的标的，20% 的线又太松。
改为按标的自身近 120 日滚动标准差的 6 倍分层后降到 25 条，
命中分布从「高波动股天天报」变成 DIS、AAPL、AMD 这些本该稳的票真的异动。

## 两个视图

同一套数据，两个入口。

**日常视图（前厅）**是作为使用者看的：总览、自选股、个股详情、事件日历。
总览只回答一个问题——现在有没有需要动手的事；没有就直接去看盘。
自选股表格支持点表头排序、按市场或行业分组；个股页有复权价与成交量双图、
区间统计（涨跌、年化波动、最大回撤）和同行业对比。

**运营视图（后厨）**是作为维护者看的：异常清单、复权核对、数据覆盖、规则库、处理台账、运营报告。

「数据覆盖」这一页原本叫「次新股」、放在日常视图里，是分类错了。它回答的不是
「哪些新股值得关注」，而是「哪些标的的历史数据不够长、结论不能全信」，属于运营视角。

早上先进后厨花十分钟把数据理干净，然后回到前厅安心看盘。
前厅里每行末尾的数据质量角标，就是后厨的产出漏到前厅来的：

| 角标 | 含义 |
|---|---|
| 灰 | 今日无异常 |
| 黄 | 有异常但原因已查明，数字可用 |
| 红 | 有异常且原因未明，该行数字暂不可信 |

## 架构

```
采集层  raw_*          原样落盘，带 source / fetched_at，可重放
   ↓
事件层  events_*       公司行动、前瞻日历。整个系统的枢纽
   ↓
校验层  dq_rules       规则表：规则是数据不是代码，加规则 = 插一行 SQL
        dq_results     命中记录 + 人工处理台账
   ↓
结论层  mart_*         自算复权价、自选股快照（带质量标记）
   ↓
视图层  日常视图 ←──同一套数据──→ 运营视图
```

事件层是融合点。同一张公司行动表，运营视图用它解释价格跳空，日常视图用它提醒你该关注什么。
同样，`dq_results` 在日常视图里渲染成注脚，在运营视图里渲染成待办。写一次，两处用。

校验层同时覆盖业务数据与采集链路本身。22 条规则里，20 条查行情、公司行动、基本面这些业务数据，
另外 2 条查链路自己：`DQ-OPS-001` 查最近一轮采集有没有失败的数据集，
`DQ-SYS-001` 查最新交易日有没有按期推进。后者命中时会占据总览页最顶部，
优先级高于任何个股异常，因为数据过期时页面上其余结论全都建立在过期数据上。

`dq_results` 里的人工判断字段（status、handled_by、handled_at、handling_note）
另外导出到 `data/ledger.csv` 并提交进仓库。数据库文件不进版本库，
定时任务在 CI 里从零建库，这四个字段是全表唯一不能从 raw 层重放的部分，
必须单独持久化，否则每跑一次台账就被清空一次。

## 数据源

| 源 | 角色 | 提供 | 覆盖 |
|---|---|---|---|
| yfinance | 主源 | 日线、拆股派息、基础估值、前瞻财报日 | 港美股 |
| akshare | 副源 | 日线，仅用于跨源交叉验证 | 港美股 |
| Nasdaq 公开日历 API | — | 前瞻除息日、登记日、派付日、拆股生效日 | 仅美股 |
| 港交所披露易 | — | 公告原文与 PDF 链接 | 仅港股 |

副源存在的唯一理由是开启 `source` 域的校验。单源只能查「内部自洽」——数据源自己跟自己
有没有矛盾。如果一个源给出的值看起来合理、内部也自洽，只是数值本身错了，单源永远查不出来。
当前 35 只标的、2801 个交易日可交叉验证，两源收盘价最大偏离 0.043%，均在阈值内。

不追求覆盖度。免费源拿不到实时报价、盘口、逐笔、资金流、机构持仓、分析师预期。
**三十个敢拍胸脯的字段，比五百个不知道对不对的字段有用。**

## 用法

```bash
pip3 install yfinance akshare duckdb pandas jinja2
```

```bash
PYTHONPATH=src python3 -m mdesk.pipeline
```

全链路：采集 → 前瞻事件 → 重算复权 → 跑规则 → 更新快照 → 渲染站点。

```bash
PYTHONPATH=src python3 -m mdesk.pipeline --render
```

只重渲染，不联网。改了模板或刚填完台账时用。

```bash
PYTHONPATH=src python3 -m mdesk.handle DQ-CA-001 9988.HK 2025-06-11 \
    --status explained --note "数据源用美元金额扣减港币价格，复权价以自算为准"
```

填写处理台账。人工判断记录用独立字段存放，重跑采集和规则都不会覆盖。

站点生成在 `site/`，本地预览：

```bash
python3 -m http.server 4173 --directory site
```

改自选股编辑 `data/watchlist.csv`，改跨市场对照编辑 `data/cross_listing.csv`，
改规则编辑 `sql/rules_seed.sql`。都不需要动 Python 代码。

## 已知缺口

以下每条都对着代码或数据核过，核实依据写在条目里。

1. **副源只覆盖近四个月，跨源比对查不了历史。**
   akshare 覆盖 35 只标的、2801 行、2026-04-20 起，人均 80 个交易日；
   主源 yfinance 覆盖 43 只、19239 行、2024-08-14 起，人均 447 个交易日。
   `DQ-SRC-001` 到 `DQ-SRC-004` 只能在两源重叠的那 2801 个交易日上生效，
   更早的历史数据目前只有单源，出错也发现不了。
   另外 8 只仅作跨市场折算用的参考标的（BABA、XPEV、0005.HK、2330.TW 及四只 A 股）
   副源未覆盖，它们不参与跨源规则。

2. **港股前瞻除净日依赖人工确认。**
   前瞻除息事件里美股 1 条来自 Nasdaq 日历（带结构化的登记日与派付日），
   港股 2 条来自披露易公告标题的关键词粗筛，除净日藏在 PDF 正文里，本版不做 PDF 解析。
   页面上这两类数据有明确的来源标注，不混在一起看。

3. **无新股首日检查。**
   `events_calendar` 里 `event_type='ipo'` 的记录为 0 条。
   数据覆盖页只能从行情起点反推上市时间，无法区分「新上市」和「数据源覆盖起点晚」，
   也做不了首日字段完整性检查。

4. **告警阈值只按波动率分层，未考虑事件驱动。**
   `DQ-PRC-002` 的 SQL 只 join 了 `events_corporate_action`，没有 join `events_calendar`，
   所以财报日当天的大幅波动仍会命中，需要人工判断。财报日历已经在库里，接进规则条件即可降噪。

5. **定时任务有两个已知的静默失效场景。**
   一是 GitHub 对连续 60 天无提交的仓库会停用 schedule 触发器，届时管道会安静地不再运行；
   `DQ-SYS-001` 能发现数据过期，但要有人去看页面才行。
   二是两地同时休市且管道恰好也停了的极少数情况（元旦、圣诞），
   `DQ-SYS-001` 的 run_gap 条件会把这种情况判为休市而不告警。

## 这套东西放进组织里会长成什么样

**以下全部是设计推演，不是已实现功能。**当前 mdesk 是单人自用，没有多人协作、
没有审批、没有值班。这一节写的是若要多人用需要补什么，并逐条对照现在缺的字段与流程。

**规则的责任归属。**`dq_rules` 现有 10 个字段，没有一个和人相关。
多人场景至少要补四个：`owner_role`（谁定义并对阈值负责）、`handler_role`（命中后谁处理）、
`escalate_to`（超时升级给谁）、`review_due`（下次复核日期）。
现在这些信息散在 `note` 里，比如 DQ-CA-001 的 note 写着「2026-08-30 复检汇丰」，
是自然语言，机器读不出来也没法到期提醒。

**新增或修改规则的流程。**现在改 `sql/rules_seed.sql` 直接生效，无审批无灰度无回退。
补法是给规则加 `status`（draft / shadow / active / retired）和 `version`：
新规则先进 shadow，只写 `dq_results` 不进页面告警，跑满两周看命中量与误报率再转 active。
回退靠 `enabled=false`，这个字段已经有了，但目前没有任何流程调用它。
改阈值应当留痕，现在直接覆盖，看不出某条规则的阈值改过几次。

**异常分级与响应时限。**现有 P0 / P1 / P2 是按「数据错得多严重」定的，
和影响面无关，这是当前分级最大的问题。应当改成两个维度定级：
影响面（单标的 / 单市场 / 全量）× 下游是否已被引用。
全量且已被下游引用的定 P0，2 小时内响应；单市场未被引用的定 P2，下个工作日处理即可。
「下游是否已被引用」这个信息 mdesk 完全没有——没有血缘表，
不知道哪个字段被哪张报表用了。这是从单人工具走向平台最缺的一块。

**质量指标怎么向上汇报。**`dq_report_snapshot` 已经每天存一行，
有命中数、已关闭数、平均关闭时长。月报可以直接用，但有两个口径要先定死：
一是误报率的分子只算 `ignored` 不算 `explained`（报告页已按此实现并写明理由），
二是平均关闭时长目前样本只有 5 条、全部在同一天内关闭，
数字是 0.9 小时但不具备参考意义，需要积累到跨周的样本才能作为考核口径。
向上汇报还缺一个 mdesk 现在没有的数：SLA 达成率，
即各级异常在时限内关闭的比例，要先有 `escalate_to` 和时限字段才算得出来。
